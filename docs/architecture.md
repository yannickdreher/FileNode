# Architecture and acceptance criteria

## Boundaries

`config` contains a password-free profile. `i18n` owns presentation language and structured messages. `scanner` invalidates an in-memory fingerprint/hash cache from native events, debounces bursts and falls back to complete content verification when events are unavailable or lost. `filesystem` validates portable names, detects unsafe links and hashes full contents. `jmap` is the only HTTP adapter. `planner` is a pure three-way comparison. `activity` emits account-independent folder and per-file events, with throttled byte progress and success only after the engine commits its baseline. `group` orchestrates per-folder watchers, stores and retry deadlines while sharing account credentials and transfer budgets. `engine` applies a validated plan and rechecks state at mutation boundaries. `store` owns SQLite baseline/journal metadata and the exclusive local-folder lock. `runtime` owns transfer budgets and cooperative interruption.

There are two independent presentation projects: `apps/windows` uses C# and actual WinUI 3 controls; `apps/linux` uses C++/Qt Quick Controls with KDE desktop-style integration when installed. Both use the same Rust worker and en/de catalogs. GNOME can run the Qt frontend, but its controls are not GTK/libadwaita. See [desktop frontends](desktop-frontends.md) for build and packaging boundaries.

The desktop host remains a per-user process with a tray icon. Closing windows hides them; explicit quit stops the Rust child. `--service` names a private JSON-lines worker over inherited stdin/stdout, not a Windows SCM service or a systemd unit. No permanent IPC listener is opened; explicit browser sign-in temporarily opens an IPv4 loopback callback. Protocol version 4 is declared in `ready`; failed configuration must not trigger connection with older settings. OS credential storage, validation and synchronization stay in Rust. Presentation hosts translate structured events and forward OS power notifications. Windows uses native window/power messages; Linux uses logind PrepareForSleep and power-profiles-daemon D-Bus signals. No sleep inhibitor is registered. The worker checks policy during scanning, hashing, staging and payload transfer, aborts cooperatively and invalidates its cache after resume. An already issued HTTP request or filesystem call can finish before it observes the change. Headless mode has payload limits but no desktop power-event subscription.

Packaged Windows startup uses StartupTask and honors OS/user restrictions; unpackaged Windows uses the current user Run key. Linux uses XDG autostart. No elevated service is installed. The worker retains its HTTP client across successful cycles and reads credentials through the OS keyring.

## Synchronization invariants

1. A complete local namespace scan and consistent remote snapshot precede planning. Missing/failed listings are errors, never empty listings.
2. Initial absence cannot imply deletion. Deletion needs a previous baseline and an enabled propagation setting. New profiles enable it; explicit existing settings are retained. Changed content wins over deletion. A dirty descendant prevents deletion of its directory.
3. Remote overwrites, moves and creates include the snapshot-derived `ifInState`. A private version copy is created before replacing remote content. Deletes use the shared server trash and restore batches, distinct from version history. No retry blindly repeats a mutating request whose outcome is uncertain.
4. Final local verification checks content again before replacement. Downloads are staged and fsynced, then renamed on the same filesystem. Previous local contents are moved to history; conflicts remain inside the sync tree as siblings. This reduces races but is not a transaction against other local applications.
5. Each newly selected folder maps to its final name at the server root; only the leaf tree is synchronized and pinned by ID. Overlapping selections and unsafe names are rejected. Missing pinned server roots or unavailable local roots cannot cause silent recreation or mass deletion. Removing a selection changes no user files.
6. A profile identity binds server, username, explicit account selection, canonical local path and remote folder. Discovery additionally pins the actual account ID. Only one process owns a local state store.
7. State changes follow completed file operations. On restart, current local/remote state is inspected again; a pending journal entry is evidence, not an instruction to blindly replay. Some recovery copies can be duplicated after a crash; preserving content takes priority over deduplicating history.
8. No authenticated request follows a different origin (scheme, host or port). Discovery redirects are bounded and manually checked. Advertised endpoint templates are checked before use. Passwords are never written to logs/config; server error payloads are not dumped.
9. Remote paths cannot escape the chosen folder, use Windows special names, contain path separators, collide after NFC/case folding or traverse symlinks/reparse points. The account and local user are trusted: the client is not a sandbox against a malicious process with the same filesystem permissions. OS-level permission/ACL isolation and independent backups remain necessary.
10. Language changes affect rendering only. English keys, persisted paths, protocol schema, conflict suffixes and three-way decisions do not vary by locale. Arguments are substituted once so braces in file names cannot rewrite other arguments.

## Test coverage

Unit/property tests exercise the three-way matrix, mass-deletion limits, first-sync behavior, simultaneous edits, path traversal, reserved Windows names, normalization collisions, content hashing, symlink rejection, catalog parity, locale selection and live message rendering. Scanner tests exercise zero rehash on idle, same-size/same-mtime edits signaled by events, overflow/error invalidation and ignored internal paths. An integration test asserts that idle cycles do not rewrite unchanged baseline/snapshot records. Multi-folder integration tests cover Unicode nested paths, sibling isolation, overlapping selections, unavailable-drive recovery, stop-without-deletion and shared power gating. Loopback HTTP contract tests cover session discovery, legacy/modern schemas, paged snapshots, changes, uploads, conditional writes, resumed downloads and endpoint origin containment.

Stateful integration tests use real files/SQLite plus immutable in-memory remote blobs. They cover idempotence, initial upload, remote edits, both-side conflicts, ambiguous create after server commit, overwrite backups, both deletion directions, delete-versus-edit, local and remote renames, failed listings, concurrent remote state changes, missing roots, profile/lock protection and file/directory conflicts.

The isolated Linux desktop smoke test registers a Qt StatusNotifier tray over D-Bus, closes the window without exiting, reactivates it through the tray, opens settings and quits through the menu. Rust integration tests additionally cover locked-file deferral with unrelated progress, write-settling, power interruption and the desktop protocol. Windows native core tests, WinUI compilation and unsigned MSIX creation are separate checks. Compilation and packaging do not establish interactive WinUI/Explorer behavior or Microsoft Store certification.

Changed files wait for a configurable stable observation interval (default two seconds). Windows snapshots deny sharing with writers while held. Unix locks are advisory and only coordinate with cooperating applications. Deferred entries protect their whole top-level subtree from planning, including deletions and renames. This is conservative and can delay siblings. A writer can pause longer than the settling interval or race after verification; this is not a universal write-completion detector or filesystem transaction.

Upload/download payload caps are independent, configurable in KiB/s, and applied in bounded 16 KiB chunks without an initial burst. Zero means unlimited. The directional schedules are shared by all concurrent uploads and folders; metadata commits and downloads remain serial. See [transfer limits, push and reconnection](transfers.md). TLS overhead, OS/socket buffering and HTTP metadata are outside these payload caps; they are not exact network-interface wire-rate limits.

These tests do not establish live server interoperability or arbitrary power-loss durability. SQLite synchronous FULL and file fsync are used, but all containing directory entries are not explicitly fsynced. Remote blob IDs are opaque; downloads validate TLS, advertised length and local SHA-256, without an independent server-provided content digest. Existing full-size staged downloads assume the local private directory is trustworthy.

## Follow-up acceptance work

- Exercise an isolated Stalwart 0.16.27 account and the intended newer server version through Bulwark and two desktop devices. Verify quotas, FileNode limits, hidden recovery-folder visibility, app-password permissions and changes retention.
- Run interrupted-transfer, disk-full, locked-file, database corruption, network partition, sleep/resume and forced-kill campaigns on native Windows NTFS and Linux ext4. Record outcomes before broad deployment.
- Expand directory/case-only rename handling, robust local race isolation, account/snapshot consistency validation and history restore/indexing. Add Retry-After support, jitter and offset-resumable uploads. Concurrent budgets and WebSocket push invalidation retain periodic reconciliation. Local namespace enumeration remains O(n); the cache reduces content I/O, not directory-walk complexity. The cache is intentionally not trusted across process restarts, and all files are rehashed at startup and after reconnecting.
- Define retention, storage quotas, selective sync and a recoverable conflict/restore workflow.
- Complete live OAuth/OIDC-provider acceptance with file-scoped tokens; see [browser authentication](browser-authentication.md). The implemented client never embeds a secret.
- Implement files on demand separately per OS (Windows Cloud Files API; a Linux virtual filesystem), including hydration/eviction, dirty-file pinning, offline behavior and permission models.
- Expand native Windows acceptance, additional Linux desktop integration, signed installers, update verification, dependency/security scanning and release acceptance gates.

Until these gates pass, distribute this client as a preview and validate a dedicated test folder before connecting valuable data.
